> 版本：v0.1
> 日期：2026-06-03
> 配套：PRD.md（v0.2）、UX-交互设计.md（v0.3）
> 目标：把需求与交互落成一套可开工的技术蓝图

---

## 0. 架构总原则

源自前序决策，作为架构硬约束：

1. **云端单一部署**（不做私有化硬约束，但容器化以便将来平滑迁移）
2. **模型走 OpenAI 兼容接口**，业务层不绑定厂商，模型可配置可替换
3. **规则引擎 + 大模型 + RAG 三者结合**：确定性检查交规则，语义研判交模型，知识召回交 RAG
4. **可溯源是底线**：每条意见必须能精确定位回原文位置（本架构的最大技术难点）
5. **异步 + 流式**：审查耗时长，任务异步化、意见流式产出

## 2. 技术选型（推荐栈）

| 层 | 选型 | 理由 |
|----|------|------|
| 前端 | **React + TypeScript + Vite** | 生态成熟，适合复杂工作台 |
| 文档渲染 | PDF.js（PDF）、docx 转 HTML 渲染 | 支持高亮定位与坐标映射 |
| 状态管理 | Zustand / Redux Toolkit | 四区联动状态较复杂 |
| 后端 | **Python + FastAPI** | AI/文档解析生态最强，异步友好 |
| 异步任务 | **Celery + Redis**（或 RQ） | 审查任务异步化、可水平扩展 |
| 流式 | SSE（Server-Sent Events） | 意见边生成边推送，比 WebSocket 简单 |
| 数据库 | **PostgreSQL** | 关系数据 + JSONB 灵活 |
| 向量检索 | **pgvector**（MVP）→ Qdrant/Milvus（规模化）| MVP 省一个组件，复用 PG |
| 对象存储 | S3 兼容（MinIO / 云 OSS）| 存原始文档与导出报告 |
| 文档解析 | PyMuPDF/pdfplumber、python-docx、PaddleOCR(Phase2) | 版式+表格+OCR |
| 模型接入 | OpenAI Python SDK（指向兼容 endpoint）| 落实接口决策 |

> 选 Python 后端的核心理由：文档解析与 LLM 编排生态在 Python 侧最完整，
> 团队若更熟 Node/Java 也可替换，架构分层不变。

## 3. 审查流水线（核心数据流）

一份文档从上传到出报告，走以下流水线（异步、分阶段、可流式）：

```
[上传] 原始文件 → 对象存储
   │
[① 解析] PDF/Word → 结构化文本(章节/条款/表格) + 每段保留 位置坐标(页/偏移)
   │
[② 切分] 按条款/语义切块(chunk)，每块带 唯一ID + 原文定位锚点
   │
[③ 要素抽取] LLM 抽取合同要素 → 合同档案卡（主体/金额/期限/付款…）
   │
[④ 规则校验] 规则引擎跑硬规则：缺失条款、金额大小写一致、交叉引用… → 生成规则类意见
   │
[⑤ RAG 检索] 每个 chunk 检索 红线库/法规/历史案例 → 召回相关知识
   │
[⑥ LLM 研判] chunk + 召回知识 + 立场 → LLM 输出语义类意见（含原文引用、依据、建议）
   │         （流式产出，前端边收边显示）
   │
[⑦ 定位回填] 把每条意见的"原文引用"精确映射回原文坐标（可溯源核心，见 §5）
   │
[⑧ 评分] 评分引擎按可配置规则汇总 → 整体风险评分 + 分级
   │
[⑨ 汇总] 落库 → 前端工作台展示 → 可生成报告
```

**规则与模型的分工**（关键设计）：
- **规则引擎**：确定性、可枚举的检查（缺条款、金额前后不一致、日期逻辑、引用有效性）
- **大模型**：语义性、需研判的检查（条款是否失衡、表述是否模糊、风险解读）
- 两类意见合流、去重，统一定位与评分。

## 4. 模型网关（OpenAI 兼容接入层）

落实「统一 OpenAI 接口 + 模型可替换」决策。所有 LLM 调用收口到一个网关模块：

```
ModelGateway
 ├─ 配置：base_url / api_key / model / temperature / max_tokens / timeout
 ├─ 能力：chat completion（流式 & 非流式）、结构化输出(JSON mode)、function calling
 ├─ 容错：超时重试、限流退避、失败降级（仅保留规则类意见兜底）
 ├─ 可观测：调用日志、token 计数、成本统计
 └─ 多模型路由(可选)：抽取用便宜模型，研判用强模型
```

- 业务代码只依赖 `ModelGateway`，**永不直接写死某厂商**。
- 换模型/换网关只改配置，无需改业务。
- 结构化输出统一用 JSON Schema 约束，保证意见字段稳定（等级/原文/问题/依据/建议）。

## 5. 可溯源：意见 → 原文精确定位（最大技术难点）

这是产品信任的命门，单独设计：

**问题**：LLM 给出的"原文引用"是它复述的文字，未必与原文逐字一致，
需精确映射回原文的页码/坐标/字符偏移，才能在前端高亮。

**方案（三重保障）**：
1. **解析阶段建立锚点索引**：每个 chunk、每段、每个 token 区间都记录
   `{page, char_start, char_end, bbox}`，形成「文本↔位置」映射表。
2. **强制 LLM 引用 chunk_id + 精确 quote**：提示词要求模型对每条意见
   返回 `源chunk_id` 和 `逐字引用片段`，而非自由复述。
3. **回填时做模糊匹配兜底**：用引用片段在对应 chunk 内做
   字符串/模糊匹配(fuzzy match)，定位到精确 offset；匹配失败的意见
   标记「定位存疑」，降权或人工确认，**绝不瞎指**。

> 原则：宁可标「未精确定位」，也不给错误的高亮位置——错误定位比没定位更伤信任。

## 6. 规则引擎 与 评分引擎（均可配置）

### 6.1 规则引擎

- 规则以**配置化**形式存储（DB + DSL/JSON），分两类：
  - **结构规则**：缺失条款（对照标准条款清单）、金额大小写一致、日期逻辑、交叉引用有效性
  - **红线规则**：命中企业红线条款库（关键词 + 语义匹配）
- 每条规则可配：适用文档类型、立场、风险等级、触发条件、提示文案。
- 规则命中直接产出意见，**确定性强、可解释、零幻觉**。

### 6.2 评分引擎（落实"可自定义规则逻辑"）

- 输入：全部意见（规则类 + 模型类）+ 评分规则配置
- 评分规则可配：高/中/低权重、一票否决项、分档阈值、按立场/类型分规则集
- 输出：整体风险评分(0-100) + 风险等级
- 配置存 DB，设置页可视化编辑（对应 UX 4.8 节）

## 7. 知识库与 RAG

| 知识库 | 内容 | 检索方式 |
|--------|------|---------|
| 红线条款库 | 企业红线（**支持批量导入存量**）| 关键词 + 向量语义 |
| 标准模板库 | 合同/标书范本（**导入存量**）| 用于条款完整性对照与模板比对 |
| 法规库 | 法律法规条文 | 向量语义检索，供依据展开 |
| 历史案例库 | 过往审查结论（人审反馈回流）| 向量语义检索，供"类似案例" |

- 入库流程：导入 → 解析切分 → 向量化(embedding) → 存 pgvector
- 检索：审查时按 chunk 语义召回 top-k，作为 LLM 研判的依据上下文
- **人审反馈回流**：驳回/修改的意见沉淀进案例库，持续提升准确率

## 8. 数据模型（核心表，简化）

```
documents        文档(id, name, type, stance, status, storage_key, created_by, ...)
doc_chunks       切块(id, doc_id, seq, text, page, char_start, char_end, bbox)  ← 定位锚点
review_tasks     审查任务(id, doc_id, status, stage, score, level, started_at, ...)
review_findings  审查意见(id, task_id, chunk_id, source[rule|llm], level, category,
                          quote, problem, basis, suggestion, status[待定/采纳/驳回/改],
                          reject_reason, locate_status)
contract_profile 合同档案卡(task_id, parties, amount, amount_check, period, payment, ...)
clause_checklist 条款完整性(task_id, clause_name, present[bool], chunk_id)
rules            规则(id, type, doc_type, stance, level, condition, message, enabled)
score_rules      评分规则(id, scope, weights, veto_items, thresholds)
kb_redlines      红线库(id, content, embedding, doc_type, stance, level, ...)
kb_templates     模板库(id, name, doc_type, content, ...)
kb_regulations   法规库(id, title, article, content, embedding)
kb_cases         案例库(id, content, embedding, source_finding_id)
audit_logs       审计日志(id, user, action, target, detail, ts)
settings         配置(model_config, scoring_config, ...)
```

## 9. 关键接口（REST，示意）

```
POST /api/documents               上传文档
POST /api/reviews                 发起审查(doc_id, stance) → task_id
GET  /api/reviews/{id}/stream     SSE 流式获取审查进度与意见
GET  /api/reviews/{id}            获取审查结果(意见/档案卡/完整性/评分)
PATCH/api/findings/{id}           采纳/驳回/修改某条意见
POST /api/reviews/{id}/report     生成报告 → 导出 PDF/Word
GET  /api/kb/redlines             知识库 CRUD
POST /api/kb/redlines/import      批量导入存量红线/模板
PUT  /api/settings/model          模型配置
PUT  /api/settings/scoring        评分规则配置
```

## 10. 非功能落地

| 需求 | 落地手段 |
|------|---------|
| 异步/性能 | Celery worker 横向扩展；50 页 ≤3 分钟；流式降低体感等待 |
| 可溯源 | §5 锚点索引 + 引用回填 + 定位存疑标记 |
| 安全 | HTTPS、密钥加密存储(KMS/加密字段)、对象存储私有桶、鉴权 |
| 审计 | audit_logs 全量留痕（谁/何时/对哪条做了什么）|
| 容错 | 模型失败降级到规则兜底；任务可重试；阶段性结果可见 |
| 可观测 | 调用日志、token/成本统计、任务监控 |
| 可解释 | 每条意见带依据(规则编号/法规/红线)，杜绝裸结论 |

## 11. 分阶段落地（与 PRD 分期对齐）

**Phase 1 / MVP（合同 + NDA）**
- 解析(电子版 PDF/Word，不含 OCR) → 切分锚点 → 要素抽取
- 规则引擎(缺失条款/金额一致/红线) + LLM 研判(失衡/模糊)
- RAG(红线+法规) + 可溯源定位 + 可配置评分
- 四区审查工作台 + 标准报告导出 + 知识库批量导入 + 模型配置
- 单人审查、Web 桌面端

**Phase 2（招投标）**
- OCR 扫描件、招标要求逐条响应比对、偏离表、多家横向比对
- 多模型路由优化成本

**Phase 3**
- 多文档关联审查、协作(指派/评论)、报告模板可配置

## 12. 主要技术风险

| 风险 | 应对 |
|------|------|
| 意见定位不准 | §5 三重保障 + 定位存疑标记，先保证不错指 |
| LLM 幻觉/漏审 | 规则兜底确定性项 + 评测集回归 + 依据强制 |
| 复杂版式解析(表格/扫描件) | MVP 限电子版；OCR 与表格解析放 Phase 2 专项 |
| 长文档成本/延迟 | 分块并发、便宜模型做抽取、缓存、流式 |
| 知识库质量 | 已有存量可导入，配清洗/去重；人审回流持续优化 |
